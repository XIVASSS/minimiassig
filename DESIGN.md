# Design

This agent remembers what was said on a real date, then checks the live web when the user asks whether that is still true. Memory is loaded before the model speaks. Web search is the only tool the model can call. The talking model is Gemini Flash.

Two memory systems were worth stealing from and not worth importing. Letta keeps a small core memory in the prompt and a larger archive behind a tool. A tool the model can skip will invent an earlier conversation, so the archive is prefetched in code, and an ordinary chat turn also gets a short open ledger: the newest stored note for each name in the question. Mem0 writes memory after the turn. The reply is already streamed before that write, so the user is not waiting on a second model call. Gemini's built-in Google Search was rejected. A verify turn has to open the URLs already stored on the claims, and this agent is allowed one search tool.

A turn parses dates in code, prefetches matching transcripts and claims from SQLite, and picks one mode: chat, recall, verify, or research. Chat and recall do not search. Verify opens the URLs stored on those claims, in parallel, before the model speaks. The ledger already names the pricing pages, and a model that picks its own query tends to search once and miss a vendor. If the question also asks what shipped, or there is no stored URL, the model must call web_search, and a step with no search is retried once. Research searches before stating a current fact. The reply is streamed, then the turn is saved and a short claim index is extracted. If extraction fails, the raw transcript remains.

Dates are not left to the model. A bare weekday is the most recent one, including today. "Last" plus a weekday is the most recent one strictly before today. A month and day with no year is that day in the current year, or the previous year if it would otherwise fall in the future. The parser uses `chrono-node` for calendar dates and its own weekday rules, in the timezone from `USER_TIMEZONE`. The prompt states the resolved day. If that day is empty but another day matches the topic, the answer uses the match and names the real day. If nothing matches, it says so.

Storage is one SQLite file through `node:sqlite`. This Node build has no FTS5 module, and a native SQLite addon would make `npm install` fragile, so each message, summary, and entity is indexed as tokens. Recall is a date window plus token overlap. There are no embeddings. The questions this is built for are dates and names. Messages keep the time they were said, not the time they were imported, so a harness can replay an earlier day with `at` on `POST /api/chat` or `npm run import`. Search looks across every session. The current thread is only there so a follow-up still points at the earlier list. Claims record subject, attribute, value, sources, and `as_of`. The transcript wins if a claim disagrees with it.

Search is still one tool. If `EXA_API_KEY` is set, the call goes to Exa. If it is empty, the same call reads the public Bing results feed and then fetches those pages directly, so a missing key does not stop a lookup. Known claim URLs are opened the same way. Five results, each a title, URL, published date, and a short excerpt. Identical fetches are cached for an hour. Pricing pages are often undated, so a price check does not filter by publish date. Launch lookups can. Page text is wrapped as data. A missing number is "couldn't verify", not "unchanged".

One streamed model does the talking. `LLM_PROVIDER` selects Anthropic or OpenAI. A second model as a router would add a round trip and a second opinion. The mode is a small set of cues in code, which is enough for a check against an earlier answer, a request to recall a day, and a new factual question.

I considered making memory a tool, putting the whole history in the prompt, letting the model choose which pages to open, letting the search vendor write the answer, driving a browser, and using a graph framework. A tool the model can skip will invent an earlier conversation. A full history hides the one day that matters and gets slower. A model-chosen search across several vendors usually checks one of them. A vendor-written answer drops the claim diff. A browser is slow and gets blocked on pricing pages. A graph framework would hide a loop that is one prefetch and one tool.

With another week I would score a frozen fixture on the right episode, the right claims, and whether each number in the answer appears in a claim or a fetched page. Then currency normalization, a bias toward domains already stored as sources, and a correction when the user says an earlier list was different.
